# Temporary Drop — 프런트엔드 전면 리디자인 PRD

작성일: 2026-10-03 KST · 버전: 1.2 · 상태: 디자인 착수용 제안

변경 사항: v1.1에서 받을 수 있는 파일의 수동 삭제와 검증 시나리오를 추가했다. v1.2에서는 사용자 제공 Assemble 디자인 시스템을 시각 기준으로 채택하고 [디자인 구현 상세계획](05-Assemble-디자인-구현-상세계획.md)을 연결했다.

## 1. 제품 정의와 이번 리디자인의 목적

Temporary Drop은 **내 기기에서 올린 파일을 다른 기기에서 받고, 정해진 시간이 지나면 접근이 종료되는 개인용 임시 파일 전달 도구**다. 개인 PC·휴대폰과 임시로 사용하는 PC 사이의 짧은 작업을 지원한다.

이번 리디자인은 사용자가 다음 세 가지를 바로 판단하고 실행하도록 프런트엔드를 처음부터 설계하는 작업이다.

1. 이 기기에서 파일을 올릴 것인가, 받을 것인가?
2. 지금 파일은 어떤 상태이며, 언제까지 받을 수 있는가?
3. 작업을 마친 뒤 이 브라우저의 접근을 어떻게 종료하는가?

제품의 핵심 경험은 **“파일을 고르고, 전달 상태를 확인하고, 다른 기기에서 받는다”**이다. 화면 구조·정보 위계·내비게이션·컴포넌트·시각 스타일·문구는 모두 재설계 대상이다. 현재 팔레트와 카드 배치, 큰 드롭 영역, 안내 사이드바를 새 디자인의 전제로 삼지 않는다.

서비스 이름 Temporary Drop과 기존 URL은 기본적으로 유지한다. 파일 전송·인증·보관 정책은 현재 API 계약을 기준으로 한다. 사용자에게 영향을 주는 전송 동작 변경은 별도 요구사항으로 명시한다.

### 문서의 적용 범위

- 이 문서는 새로운 UI 설계의 제품 요구사항이다. 실제 UI 구현과 배포는 후속 작업이다.
- 기존 [UI 명세](02-프런트엔드-UI-명세.md)의 레이아웃·색상·형태 제안을 새 디자인에 그대로 적용하지 않는다.
- 현재 동작 판단은 소스와 [API 계약](../API.md)을 우선한다. 오래된 계획의 미구현 기능을 현재 기능으로 간주하지 않는다.
- 이 문서의 목표 수치와 디자인 방향은 제안이며 사용자 조사로 검증된 결과가 아니다.

## 2. 현재 제품에서 확인한 사실

| 항목 | 현재 구현·계약 | 리디자인에 주는 조건 |
| --- | --- | --- |
| 파일 받기 | `/`, 4자리 PIN, 완료되고 만료되지 않은 파일 목록 | 인증 전에는 파일명·개수·크기를 숨긴다 |
| 완료 파일 삭제 | 받기 목록의 개별 삭제 버튼, `DELETE /api/files/:id` | 다운로드 인증에 더해 신뢰 브라우저 또는 파일 ID에 묶인 `delete_file` TOTP 권한이 필요하다 |
| 파일 올리기 | `/upload`, 6자리 Authenticator 코드 또는 신뢰 브라우저 | 다운로드 인증과 별개의 권한이다 |
| 내 기기 | `/devices`, 신뢰 브라우저 또는 관리용 재인증 | 관리 인증이 브라우저 신뢰 등록을 의미하지 않는다 |
| 공용 업로드 인증 | 새 업로드를 시작할 수 있는 시간 15분 | 자연 만료 후에도 이미 발급된 파일별 전송 권한은 유지된다 |
| 파일별 전송 권한 | 생성 시점부터 6시간 | 공용 인증 15분과 혼동하지 않는다. 무제한 전송 지속을 약속하지 않는다 |
| 다운로드 인증 | 기본 2시간, 선택 시 30일 기억 | 기억하기 기본 OFF, 공용 기기 안내 필요 |
| 보관 기간 | 1시간·6시간·24시간·3일, 현재 기본 24시간 | 최초 업로드 완료부터 계산한다 |
| 크기 정책 | 웹 파일당 32 GiB, 단축어 5 GiB | 설정 상한과 실제 검증 크기를 구분한다 |
| 선택 목록 | 현재 전송 목록 최대 50개, 빈 파일 거부 | 완료 항목도 남아 있으면 50개 한도에 포함된다 |
| 전송 처리 | 파일 2개 동시 처리, 탭 전체 part 슬롯 4개/좁은 화면 2개 | 디자인 변경만으로 동시 처리량을 늘리지 않는다 |
| 목록 조회 | cursor 기반, 기본 25개 | 로드된 개수를 전체 파일 개수처럼 표시하지 않는다 |
| 연결 복구 | 같은 탭에서 오프라인 대기·재연결 후 서버 확인 | 새로고침·브라우저 재시작 후 이어 올리기는 제공하지 않는다 |
| 저장소 정책 | 논리 용량 100 GiB, 일일 생성 승인량 200 GiB | 현재 사용자 API에 전체 잔여 용량 값은 없다 |
| 단축어 | 업로드 전용 토큰 발급·1회 표시와 API 안내 | 설치 가능한 `.shortcut` 파일과 iOS 실기기 검증은 미완료다 |

[운영 검증 기록](../PRODUCTION_VALIDATION.md)은 Chrome에서 64 MiB+1바이트까지 실제 업로드·다운로드를 확인했다고 기록한다. 이 PRD 작성 과정에서 운영 사이트의 현재 동작을 재검증하지는 않았다. iPhone/Safari·GiB 단위 전송·전체 접근성 검증은 기존 기록에서도 남은 작업이다.

## 3. 해결할 문제와 설계 가설

아래 진단은 현재 코드와 저장된 화면 캡처를 읽은 결과다. 실제 사용자의 불만이나 행동 데이터로 확정한 문제는 아니다.

| 관찰 | 설계 가설 | 새 UI에서 검증할 변화 |
| --- | --- | --- |
| 큰 드롭 영역과 반복 안내가 전송 목록보다 먼저 넓은 공간을 차지한다 | 파일을 선택한 뒤에는 전송 상태가 더 중요하다 | 선택 전/후에 작업 영역의 무게중심을 전환한다 |
| 공용 인증 안내가 badge·banner·보조 영역에 분산된다 | 권한 상태와 다음 행동을 한곳에 모으면 판단이 빠르다 | 일관된 접근 상태 영역에 모드·잔여 시간·종료 행동을 배치한다 |
| 받기·올리기·기기 관리가 동일한 메뉴 위계다 | 반복적인 파일 전달과 드문 관리 작업의 우선순위가 다르다 | 받기/올리기를 주 내비게이션, 기기 관리를 보조 위치에 둔다 |
| 전송 상태마다 행 높이와 액션 배치가 달라진다 | 안정된 목록 구조가 여러 파일을 비교하기 쉽다 | 파일명·상태·진행·행동의 위치를 상태 간 일관되게 유지한다 |
| 다운로드 잠금과 전체 접근 종료의 효과가 다르다 | 종료 행동에 범위를 명시해야 오해를 줄일 수 있다 | 다운로드 잠금·공용 접근 종료·기기 권한 해제를 구분한다 |
| 영어 보조 문구와 장식 기호가 작업 정보 사이에 들어간다 | 짧은 한국어 안내와 일관된 아이콘이 스캔에 유리하다 | 제품명 이외의 장식성 영문을 줄이고 정보 위계를 재설계한다 |

## 4. 대상 사용자와 주요 과업

이 제품은 한 개인이 여러 기기에서 사용하는 상황을 우선한다. 협업 조직·공개 수신자·다수 계정의 역할 체계는 이번 범위에 포함하지 않는다.

| 사용 상황 | 해야 할 일 | 성공 조건 |
| --- | --- | --- |
| 개인 PC에서 자주 보내기 | 신뢰 브라우저에서 파일 선택·보관 설정·업로드 | 불필요한 재인증 없이 시작하고 완료 여부를 안다 |
| 임시 PC에서 파일 받기 | PIN 입력·파일 확인·다운로드·잠금 | 파일을 찾고 작업 후 새 목록/다운로드 접근을 종료한다 |
| 전달을 마친 파일 정리 | 받기 목록에서 대상 파일 확인·삭제 | 선택한 파일만 삭제하고, 복구 불가와 다른 기기에서의 접근 종료를 이해한다 |
| 임시 PC에서 파일 보내기 | TOTP 입력·일시 업로드·접근 종료 | 신뢰 등록 없이 사용하고 인증 만료의 영향을 이해한다 |
| 느리거나 불안정한 연결 | 전송 대기/재시도 상태 확인 | 자동 복구와 새로 시작이 필요한 상황을 구별한다 |
| 기기를 분실하거나 교체 | 대상 기기 확인·재인증·권한 해제 | 선택한 등록만 해제하고 영향 범위를 이해한다 |
| iPhone 단축어를 직접 설정 | 전용 토큰 생성·복사·안내 확인 | 토큰의 권한과 1회 표시를 알고 설치 지원 범위를 오해하지 않는다 |

## 5. 목표와 성공 지표

목표는 재방문 빈도·체류 시간 증가가 아니라 **적은 판단으로 전송 작업을 정확히 끝내는 것**이다. 현재 정량 기준선은 없으며 첫 설계 검증에서 측정한다.

| 지표 | 제안 목표 | 측정 방법 |
| --- | --- | --- |
| 첫 행동 발견 | 처음 보는 사용자 5명 중 4명 이상이 5초 안에 받기/올리기 진입 행동을 찾음 | 과업을 읽은 뒤 첫 화면에서 관찰 |
| 업로드 준비 | 신뢰 브라우저, 파일 1개, 기본 보관 기간: UI 행동 2회로 선택→시작 | 파일 선택 버튼과 업로드 시작 버튼, OS 선택창 내부 행동 제외 |
| 다운로드 시작 | 잠금 해제 후 대상 파일 다운로드 행동 1회 | 대상 행에서 버튼을 찾고 누르는지 관찰 |
| 과업 완수 | 사용자 5명 중 4명 이상이 작은 파일 전달과 공용 접근 종료를 도움 없이 완료 | 두 브라우저를 이용한 과업 시험, 전송 대기 시간 별도 기록 |
| 상태 이해 | 5명 중 4명 이상이 ‘인증 만료’, ‘파일 확인 중’, ‘파일 보관 만료’를 정확히 설명 | 동일한 상태 시안을 보여주고 짧게 질문 |
| 위험한 기본값 | 신뢰 등록·PIN 기억 자동 선택 0건, 인증 전 파일 정보 노출 0건 | 상태별 자동/수동 검사 |
| 회귀 | 페이지 이동·재인증으로 활성 업로드가 재생성되거나 중단되는 사례 0건 | 기존 엔진 테스트와 브라우저 통합 검증 |

5명 시험은 초기 설계 문제를 찾는 기준이며 전체 사용자 성능에 대한 통계적 보장은 아니다. 상시 분석 서비스 도입은 필수 요구사항이 아니다. 평가 기록에는 합성 파일과 익명 과업 결과를 사용한다.

## 6. 범위와 우선순위

**P0는 리디자인 출시 필수, P1은 후속 개선, 제외는 별도 제품 결정이 필요한 기능**이다.

| 우선순위 | 내용 |
| --- | --- |
| P0 | 새로운 시각 체계·앱 구조·반응형 내비게이션 |
| P0 | PIN/TOTP/관리 재인증, 각 권한의 독립 상태 표현 |
| P0 | 선택→검토→시작, 보관 설정, 전송 상태 전체, 취소·복구 안내 |
| P0 | 파일 받기 목록, 만료, 새로고침, 더 보기, 다운로드 잠금, 완료 파일 개별 삭제 |
| P0 | 공용 접근 종료, 기기 목록·권한 해제, 단축어 토큰 1회 표시 |
| P0 | 로딩·빈 목록·부분 오류·오프라인·권한 만료·처리 지연 화면 |
| P0 | 키보드·모바일·스크린리더 핵심 과업과 개인정보 보호 |
| P1 | 받기 목록의 검색·정렬. 전체 목록을 대상으로 하려면 API 계약 추가 필요 |
| P1 | 충분한 속도 표본이 있는 경우 예상 완료 시간. 불안정한 상태에서는 숨김 |
| P1 | 완료/취소 이력 일괄 정리. 서버 파일 삭제와 명확히 분리 |
| 제외 | 회원 가입, 다중 계정, 팀 협업, 결제, 공개 공유 링크, 수신자 초대 |
| 제외 | 폴더 관리, 파일 내용 미리보기, 파일 편집, 완료 파일 보관 연장·일괄 삭제 |
| 제외 | 브라우저 재시작 후 업로드 복원, 탭을 닫은 뒤 백그라운드 전송 보장 |
| 제외 | 저장소 운영 대시보드, quota 복구·고아 객체 삭제 등 유지보수 UI |
| 제외 | 새 `.shortcut` 설치 파일 제작, 인증 수단 변경, 저장소/DB 재설계 |

다크 모드·다국어는 첫 출시 필수 범위에서 제외한다. 기본 테마에서도 밝기·대비·모바일 사용성을 충분히 검증한다.

## 7. 정보 구조와 전역 경험

| 기존 URL | 화면 이름 | 핵심 행동 | 내비게이션 위치 |
| --- | --- | --- | --- |
| `/` | 파일 받기 | PIN 인증, 파일 다운로드·개별 삭제 | 주 메뉴 |
| `/upload` | 파일 올리기 | 업로드 인증 또는 파일 선택·전송 | 주 메뉴 |
| `/devices` | 내 기기 | 관리 인증·등록 확인·권한 해제 | 보조 메뉴, 한 번의 클릭/탭으로 접근 |

별도 랜딩 페이지를 추가하지 않는다. `/`에 접속하면 받기 과업으로 바로 진입하고, 올리기는 인증 전에도 쉽게 찾을 수 있어야 한다. 브랜드 링크는 `/`로 통일하는 것을 제안한다. 직접 URL 진입·뒤로/앞으로 이동·페이지 새로고침의 경로 해석을 유지한다.

전역 구조는 다음 세 층으로 설계한다.

1. **작업 선택:** 받기·올리기·기기 관리 진입점과 현재 위치.
2. **접근 상태:** 현재 화면의 권한, 필요한 인증, 범위가 명시된 잠금/종료 행동.
3. **작업 공간:** 파일 선택·대기 검토·전송 목록 또는 받을 파일 목록.

받기와 올리기 권한을 합쳐 ‘로그인됨’ 하나로 표현하지 않는다. 주 화면 이동은 같은 탭의 전송 엔진을 유지한다. 다른 화면에서도 활성 전송 요약을 노출하고 한 번에 전송 목록으로 돌아갈 수 있게 한다. 인증·연결 조회 오류가 생겨도 기존 전송 목록을 가리는 전체 오류 화면으로 대체하지 않는다.

## 8. 디자인 경험의 방향

### 채택한 시각 기준: Assemble Design System v1.0

사용자가 제공한 시스템의 `#F8F8F8` 배경·white surface·검정 텍스트·`#F1FD82` lime·4px grid·20px 카드·pill 버튼·최소 border/shadow를 새 UI의 시각 기준으로 사용한다. 폰트 권한·한국어 줄 높이·입력 식별·대비와 작업 화면의 여백 보완은 [구현 상세계획](05-Assemble-디자인-구현-상세계획.md)에 명시한다.

아래 A/B/C는 동일한 Assemble 시각 체계 안에서 구조를 비교하는 안이다. 기본안 A를 상세화했으며 구조 선택 전까지 최종 배치를 확정한 것으로 간주하지 않는다.

### 권장 방향: 전송 상태가 중심인 작업 공간

새 UI는 파일을 전달하는 짧은 작업에 집중한다. 첫 화면은 행동을 쉽게 고르게 하고, 파일을 선택한 다음에는 파일 목록과 진행 상태가 화면의 중심이 된다.

- **정보 위계:** 파일명·주요 행동·현재 상태 → 진행량/보관 시간 → 인증·연결 설명 → 추가 도움말 순서.
- **레이아웃:** 반복 안내를 상시 사이드바에 쌓기보다 작업 위치에 짧게 연결한다. 별도 패널은 실제 입력·검토 과업이 있을 때 사용한다.
- **파일 표현:** 넓은 화면은 비교하기 쉬운 행, 좁은 화면은 같은 정보 순서를 유지한 세로 목록. 파일마다 과도한 독립 카드 장식을 넣지 않는다.
- **색상:** 기본 작업색과 진행/성공/주의/실패 역할을 정의한다. 현재 녹색 팔레트에 묶이지 않되 색만으로 상태를 전달하지 않는다.
- **타이포그래피:** 한국어 읽기와 긴 파일명에 우선순위를 둔다. 수치·시간·진행량에는 자리 폭이 안정된 숫자를 사용한다.
- **아이콘:** 같은 계열의 SVG 아이콘을 사용하고 의미가 필요한 행동에는 라벨을 병기한다. 제품 아이콘을 문자 기호나 이모지에 의존하지 않는다.
- **모션:** 선택·전송 시작·상태 변경을 이해시키는 짧은 전환만 사용한다. 전송 중 반복 장식 애니메이션은 필수가 아니다.
- **브랜드:** 로고·포인트색·일관된 파일/전송 표현에서 개성을 만들고, 긴 슬로건이나 마케팅 히어로로 작업을 밀어내지 않는다.

색상·서체·모서리·컴포넌트 수치는 채택한 Assemble 시스템과 구현 상세계획을 따른다. 기존 Temporary Drop의 녹색 토큰을 재사용하도록 강제하지 않는다.

### 후속 디자인 비교안

실제 구현 전에 동일한 기능·예시 파일·상태로 세 방향을 비교한다.

| 이름 | 중심 표현 | 비교할 질문 |
| --- | --- | --- |
| A. 전송 데스크 | 간결한 내비게이션과 밀도 있는 파일 목록 | 반복 사용자에게 상태 비교와 조작이 빠른가? |
| B. 전달 단계 | 선택→검토→전송→받기의 단계 중심 | 처음 쓰는 사람이 다음 행동을 더 쉽게 이해하는가? |
| C. 파일 트레이 | 파일 묶음과 올리기/받기 두 작업 영역 중심 | 데스크톱과 모바일에서 공간 구성이 직관적인가? |

세 안은 색만 바꾸지 않고 구조와 정보 위계를 달리한다. 각 안에 완료 파일의 개별 삭제와 확인 흐름을 포함한다. 비교용 시안에서도 아직 없는 공유 링크·일괄 삭제·백그라운드 복구를 작동 가능한 기능처럼 보여주지 않는다.

## 9. 화면별 기능 요구사항

### 9.1 인증 화면 — FR-AUTH

- **FR-AUTH-01:** PIN은 4자리 단일 입력, TOTP는 6자리 단일 입력으로 구현한다. 숫자 키패드·붙여넣기·Enter 제출·읽을 수 있는 라벨을 제공한다. 자리수가 채워져도 자동 제출하지 않는다.
- **FR-AUTH-02:** PIN 마스킹, TOTP `one-time-code` 자동완성을 지원한다. 기억하기·신뢰 등록은 기본 OFF다.
- **FR-AUTH-03:** 신뢰 등록을 선택한 경우에만 기기 이름을 입력받고, 해당 브라우저에 지속적인 업로드 권한이 생긴다는 것을 설명한다.
- **FR-AUTH-04:** 입력 오류·잘못된 코드·이미 사용한 코드·시도 제한·네트워크 실패를 구분한다. 재시도 시간은 서버 `Retry-After`를 기준으로 하며 임의의 2분 안내를 하드코딩하지 않는다.
- **FR-AUTH-05:** 인증 요청 중 중복 제출을 막고 상태를 알린다. 성공 후 PIN/TOTP 입력 값을 지운다. 오류 후에는 수정할 입력에 접근하기 쉽도록 한다.
- **FR-AUTH-06:** 업로드 재인증은 기존 전송을 유지한 채 수행한다. 관리 인증에 신뢰 등록 옵션을 섞지 않는다.

### 9.2 업로드 — FR-UP

- **FR-UP-01:** 파일 선택 버튼으로 모바일·키보드에서 완전한 과업 수행이 가능해야 한다. 드래그 앤 드롭은 데스크톱 보조 수단이다. 페이지 밖 드롭으로 탭이 파일 화면으로 이동하지 않도록 방어한다.
- **FR-UP-02:** 선택 파일은 검토 대기 목록에 들어간다. 개수·총 선택 용량·파일명·크기·완료 후 보관 기간을 확인하고 명시적으로 업로드를 시작한다.
- **FR-UP-03:** 추가로 선택한 파일도 각각 사용자가 시작을 승인하기 전에는 전송하지 않는다. 이미 시작한 파일은 계속 진행한다. 현재 엔진의 `enabled` 상태와 대기열 처리를 조정해야 하는 동작 변경이며 CSS 변경으로 대체할 수 없다.
- **FR-UP-04:** 기본 보관 기간은 24시간, 선택지는 1시간·6시간·24시간·3일이다. 기본값 변경은 이후 선택 파일에만 적용한다. 기존 대기 파일은 개별 변경하고 서버 생성 이후에는 변경하지 못한다.
- **FR-UP-05:** 빈 파일·파일당 상한 초과·목록 50개 초과를 전송 전에 알린다. 현재 엔진처럼 한 선택 묶음에 잘못된 파일이 있으면 묶음 전체를 추가하지 않고 이유와 다음 행동을 표시한다.
- **FR-UP-06:** 선택 전에는 파일 선택이 중심이고, 선택 후에는 검토 목록, 시작 후에는 진행 목록이 중심이 된다. 파일 추가 행동은 계속 찾기 쉬워야 한다.
- **FR-UP-07:** 전송 목록은 파일별 상태·진행량·속도·오류·가능한 행동을 보여준다. 예상 시간은 P1이며 임의의 정밀 수치를 표시하지 않는다.
- **FR-UP-08:** 100% 전송 후에도 서버가 READY를 확인하기 전에는 ‘파일 확인 중’이다. 완료 이후에만 ‘업로드 완료’, 만료 시각, 받기 화면 이동을 제공한다.
- **FR-UP-09:** 공용 인증 만료 시 새 파일 시작을 막고 재인증을 제시한다. 기존 활성 전송·파일별 권한·진행량은 유지하며 재인증 이후에도 같은 전송을 새 업로드로 만들지 않는다.
- **FR-UP-10:** 취소는 대상 파일명이 보이는 확인 절차를 거친다. 취소 처리 중 중복 행동을 막고 서버 확인 실패를 성공으로 표시하지 않는다. 서버가 먼저 완료 처리를 시작했다면 결과 확인으로 안내한다.
- **FR-UP-11:** 새로고침·브라우저 종료 후에는 이어 올릴 수 없다는 안내를 전송 중 행동 가까이에 둔다. 내부 메뉴 이동과 브라우저 종료를 같은 중단으로 취급하지 않는다.
- **FR-UP-12:** 완료 항목의 ‘이 화면에서 지우기’는 로컬 이력 제거다. 받기 목록의 서버 파일은 유지하며 삭제 성공 메시지를 내보내지 않는다.

### 9.3 파일 받기 — FR-DOWN

- **FR-DOWN-01:** PIN 인증 전에는 파일 정보가 보이지 않는다. 잠금 해제 직후에는 로딩 상태를 거쳐 실제 미만료 READY 파일만 표시한다.
- **FR-DOWN-02:** 행마다 파일명·크기·완료 시각·남은 보관 시간·다운로드·삭제 행동을 제공한다. 다운로드를 주 행동으로, 삭제를 구분된 위험 행동으로 배치한다. 긴 이름은 마우스 hover 없이도 전체 이름을 확인할 수 있어야 한다.
- **FR-DOWN-03:** 최근 완료순을 기본으로 하고 새로고침·cursor 더 보기를 유지한다. 개수는 ‘불러온 파일 N개’처럼 조회 범위를 명시한다. 더 보기 실패로 이미 불러온 항목이 사라지지 않아야 한다.
- **FR-DOWN-04:** 만료 판단은 서버 시각 보정을 사용한다. 만료 파일은 다운로드 불가로 전환하고 목록에서 제거한다. 파일 접근 만료와 저장소 물리 삭제 완료를 같은 시점이라고 표현하지 않는다.
- **FR-DOWN-05:** 다운로드 클릭으로 요청을 시작할 수 있어야 한다. 페이지가 브라우저의 파일 저장 완료를 확인하지 못하면 ‘다운로드 완료’라고 표시하지 않는다. 현재 직접 다운로드 링크만으로는 서버 오류를 항상 UI에서 감지할 수 없으므로 감지 가능한 오류에만 안내를 제공한다.
- **FR-DOWN-06:** 최초 목록 실패와 이후 갱신 실패를 구분한다. 갱신 실패에는 기존 미만료 목록·마지막 확인 시각·재시도 행동을 유지한다. 세션 만료·401은 목록을 즉시 비우고 재인증을 요구한다.
- **FR-DOWN-07:** ‘다운로드 잠금’은 새 목록 조회·다운로드 요청의 접근 종료다. 업로드를 중단하거나 브라우저에 이미 받은 파일을 지우는 기능처럼 안내하지 않는다.
- **FR-DOWN-08:** 각 받을 수 있는 파일에 ‘삭제’ 버튼을 제공한다. 행 전체 클릭이나 다운로드 클릭으로 삭제되지 않아야 하며, 접근성 이름에 대상 파일명을 포함한다. 삭제는 선택한 파일 ID에만 적용한다.
- **FR-DOWN-09:** 삭제 전 확인 창에 전체 파일명과 ‘삭제 후 다른 기기에서도 새로 다운로드할 수 없으며 복구할 수 없음’을 명시한다. ‘영구 삭제’와 ‘취소’를 구분하고, 취소/Escape로 닫으면 삭제 요청을 보내지 않는다. 업로드 화면의 ‘이 화면에서 지우기’와 효과를 혼동하지 않도록 한다.
- **FR-DOWN-10:** 삭제에는 유효한 다운로드 세션이 필요하다. 신뢰 브라우저는 확인 후 추가 TOTP 없이 삭제하고, 신뢰되지 않은 브라우저는 파일 ID에 묶인 새 `delete_file` TOTP 권한을 발급받아 ‘인증하고 영구 삭제’를 실행한다. PIN만으로는 삭제할 수 없으며 공용 업로드 인증이나 일반 관리 인증으로 대체하지 않는다. 이 조건은 현재 Worker 구현을 기준으로 한다.
- **FR-DOWN-11:** 인증/삭제 처리 중 중복 제출과 대상 변경을 막고 ‘삭제 중…’을 표시한다. 서버가 `DELETED`를 확인한 뒤 대상 행을 제거하고 대상 파일명이 포함된 완료 안내와 목록 갱신을 제공한다. 삭제된 파일을 재요청해도 다른 파일을 삭제하거나 용량을 중복 반환하지 않아야 한다.
- **FR-DOWN-12:** 인증 실패·권한 만료·삭제 진행 중·저장소 정리 실패를 구분한다. `DELETE_IN_PROGRESS`는 삭제 완료로 표시하지 않고 갱신을 안내한다. `DELETE_FAILED`는 파일이 목록에서 숨겨졌으나 저장소 정리가 지연되어 자동 재시도된다는 사실을 표시한다. 목록에 없다는 이유만으로 물리 삭제 완료를 선언하지 않는다. 오류 위치와 목록을 서버 상태에 맞춰 갱신한다.
- **FR-DOWN-13:** 삭제는 이미 기기에 저장한 파일이나 이미 시작된 다운로드의 수신 바이트를 회수하지 않는다. 발급된 다운로드 URL의 회수 가능성을 보장하지 않으며, ‘모든 사본을 삭제’ 또는 즉각적인 전체 전송 중단을 약속하지 않는다.

### 9.4 접근 종료와 기기 관리 — FR-ACCESS

- **FR-ACCESS-01:** 공용 업로드 인증이 있는 동안 ‘이 브라우저에서 종료’를 찾기 쉽게 제공한다. 다운로드 화면에서도 해당 인증이 있으면 전체 공용 접근 종료로 진입할 수 있다.
- **FR-ACCESS-02:** 종료 확인에는 대상 브라우저, 종료되는 업로드/다운로드 권한, 취소 가능한 전송의 수를 표시한다. FINALIZING/READY 파일을 무조건 취소한다고 약속하지 않는다. 처리 단계에 따라 완료될 수 있음을 설명한다.
- **FR-ACCESS-03:** 단순 logout은 신뢰 브라우저 등록을 해제하지 않는다. 신뢰 기기에서는 ‘업로드 권한 해제’로 `/devices`의 대상별 TOTP 흐름에 연결한다. 다운로드만 잠그는 행동과 구분한다.
- **FR-ACCESS-04:** 기기 목록에는 이름·브라우저/단축어 유형·현재 등록 여부·마지막 사용 시각·업로드 권한 범위를 보여준다. 하드웨어나 다른 브라우저의 상태까지 식별한다고 표현하지 않는다.
- **FR-ACCESS-05:** 권한 해제는 선택한 기기 ID에 묶인 새 TOTP로 수행한다. 확인 창에서 대상 이름과 후속 전송 차단을 명시하고, 실패 시 행을 유지한다. 현재 기기 해제 후에는 인증 상태와 활성 전송 상태를 다시 확인한다.
- **FR-ACCESS-06:** 단축어 연결은 이름 입력→새 TOTP→토큰 1회 표시→설정 안내 순서다. 복사 성공/실패를 표시하고 수동 선택·복사 수단도 제공한다. 토큰은 닫으면 화면 메모리에서 제거한다.
- **FR-ACCESS-07:** 토큰 표시 단계에서 닫기/Escape 이전에 ‘저장하지 않았다면 다시 확인할 수 없음’을 확인할 수 있어야 한다. 분실 시 기존 등록을 해제하고 새 토큰을 만들도록 안내한다.
- **FR-ACCESS-08:** ‘단축어 연결’이 실제 iPhone 설치 완료를 의미하지 않게 한다. 설치 파일 미제공·실기기 검증 필요를 설정 안내에 명시한다.

## 10. 전송 상태와 가능한 행동

아래 상태명은 현재 `QueueState`와 일치한다. 상태별로 기본·좁은 화면·접근성 읽기·오류 위치를 설계 산출물에 포함한다.

| 상태 | 사용자에게 보이는 문구 | 진행 표시 | 허용 행동 |
| --- | --- | --- | --- |
| `queued` | 업로드 대기 | 없음 | 보관 기간 변경, 제거, 명시적 시작 |
| `needs_auth` | 인증 후 시작할 수 있어요 | 기존 값 유지 | 재인증, 보관 기간 변경, 제거 |
| `creating` | 전송 준비 중 | 준비 표시 | 취소 요청 |
| `uploading` | 전송 중 | 전송량·%·측정 속도 | 취소 요청 |
| `retrying` | 전송 결과를 확인하고 다시 연결 중 | 엔진이 제공하는 현재 값 | 취소 요청 |
| `offline` | 인터넷 연결을 기다리는 중 | 마지막 확인 값 | 취소 요청. 오프라인에서는 서버 확인이 지연될 수 있음 |
| `finalizing` | 파일 확인 중 | 100%라도 완료 표현 금지 | 결과 대기, 중복 완료/취소 금지 |
| `ready` | 업로드 완료 | 완료 표시·만료 시각 | 받기 화면 이동, 이 화면에서 지우기 |
| `cancel_pending` | 취소 확인 중 | 현재 값 유지 | 중복 취소 금지, 결과 대기 |
| `cancelled` | 취소됨 | 완료 체크와 구별 | 이 화면에서 지우기 |
| `failed` | 업로드를 끝내지 못했어요 | 오류 이유와 현재 값 | 원인에 맞는 새로 시작/취소 확인 |

`failed`가 항상 서버 파일 실패를 뜻하지는 않는다. 특히 `FINALIZE_PENDING`은 서버 확인이 지연되는 경우이므로 완료 결과를 먼저 조회해야 하며 바로 새 업로드를 만들도록 유도하지 않는다. 취소 확인 실패도 서버 상태를 확인하기 전에는 취소 성공으로 바꾸지 않는다. 필요한 오류 구분은 UI adapter와 엔진 snapshot 계약에서 전달한다.

진행 중 전송량은 서버 수신 확정 전의 시도 바이트를 포함할 수 있다. 재시도 때 숫자가 달라질 수 있으며 UI가 이를 임의로 증가 방향으로만 고정하지 않는다. 완료 판정은 서버 READY 응답을 따른다.

## 11. 예외·오류 경험

| 상황 | 사용자 안내와 다음 행동 | 유지해야 할 정보 |
| --- | --- | --- |
| 잘못된 PIN/TOTP | 입력을 확인해 다시 제출 | 해당 인증 목적, 입력 위치 |

| 네트워크 끊김 | 같은 탭에서 연결 대기·자동 확인 | 파일별 상태·현재 진행량 |
| 저장된 part 결과 불확실 | 서버가 결과를 확인 중, 중복 전송 방지 | 현재 전송 ID·상태, 수동 강제 재전송 금지 |
| 생성 용량/동시 업로드 제한 | 서버 오류의 이유와 가능한 다음 행동 표시 | 검토 대기 목록, 이미 진행 중인 전송 |
| 목록 갱신 실패 | 마지막 확인 시각과 다시 불러오기 | 기존 미만료 파일, 인증 만료 시 예외 |
| 파일 삭제 인증 실패/만료 | 대상 파일의 삭제를 위한 재인증, 입력 오류 수정 | 대상 파일명·ID와 확인 흐름, 미실행 상태 |
| 파일 삭제 진행 중 | 다른 요청이 삭제 중임을 알리고 목록 갱신 | 서버 결과가 확정되기 전 성공 표시 금지 |
| 파일 삭제 후 저장소 정리 지연 | 목록에서 숨겨졌으며 정리는 자동 재시도됨을 안내 | 물리 삭제 완료와 접근 종료의 구분, 서버 상태에 맞춘 목록 |
| 파일 확인 지연 | 서버 결과를 다시 확인, 미확인 상태를 완료/실패로 단정하지 않음 | 원래 파일 ID·권한·상태 |
| 취소/완료 경합 | 서버의 확정 상태에 맞춰 취소 불가 또는 완료 결과 표시 | 대상 파일, 중복 시작 방지 |
| 토큰 복사 실패 | 직접 선택해 복사 | 토큰 1회 표시 단계, 민감 값 로그 금지 |

오류는 과업 가까이에 남긴다. 사라지는 toast만으로 오류를 알리지 않는다. 전체 잔여 용량·제한 해제 시각 등 API에 없는 값을 추정해 보여주지 않는다.

## 13. 반응형·접근성·성능 요구사항

### 반응형

- 320·390·768·1440px에서 모든 P0 과업을 검증한다. breakpoint는 콘텐츠에 맞춰 결정한다.
- 좁은 화면에서 파일명·상태·보관 기간·취소/다운로드·접근 종료를 숨기지 않는다.
- 기본 흐름에 가로 스크롤이 필요하지 않아야 한다. 긴 파일명과 토큰은 영역 안에서 줄바꿈/선택할 수 있게 한다.
- 고정 액션 영역은 마지막 행·포커스·오류 메시지를 가리지 않는다. 모바일 키보드와 safe area를 고려한다.
- 드래그·hover·색상·아이콘만으로 완료할 수 있는 과업을 만들지 않는다.

### 접근성

검증 목표는 [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/)다. 아래는 우선 점검 항목이며 전체 적합성 검사를 대신하지 않는다.

- 의미 있는 landmark·제목 순서·현재 메뉴 표시·입력 라벨·오류 연결·progressbar 이름과 값을 제공한다.
- 키보드만으로 인증·파일 선택·보관 설정·시작·취소·잠금·기기 해제를 수행할 수 있게 한다.
- dialog는 포커스 이동/가두기·Escape·닫은 뒤 복귀를 제공한다. 비밀의 1회 표시처럼 손실 가능성이 있는 닫기는 추가 확인 흐름을 설계한다.
- 삭제 성공으로 원래 행이 사라지면 포커스를 다음 파일의 행동 또는 목록 제목으로 이동한다. 삭제 버튼과 다운로드 버튼을 키보드·스크린리더에서도 구분한다.
- 일반 텍스트 대비 4.5:1, 큰 텍스트와 필요한 UI 상태/경계 대비 3:1을 검증한다. 포커스가 고정 영역에 가려지지 않아야 한다.
- 프로젝트의 터치 목표는 최소 44×44 CSS px로 한다. 이는 제품 기준이며 AA의 모든 타깃 최소 규정과 동일하다고 설명하지 않는다.
- 200% 텍스트 확대와 400% 브라우저 확대에서 흐름을 검사한다. 색 외에 라벨/아이콘으로 상태를 구분한다.
- 진행률의 매 변화보다 의미 있는 상태 전환을 알린다. `prefers-reduced-motion`을 따른다.
- Windows 스크린리더와 iOS VoiceOver에서 핵심 흐름을 수동 검증한다. 실기기 증거가 없으면 iOS 검증을 완료로 처리하지 않는다.

### 성능

- API 요청 대기를 제외한 버튼/선택 피드백은 100ms 안에 보이는 것을 프로젝트 목표로 한다.
- 동일 장치·브라우저·연결·production build 조건에서 현행 UI의 초기 JS 크기·첫 작업 표시 시간·목록 조작 반응을 측정한다. 10% 초과 악화는 원인을 기록하고 출시 전에 해결하거나 근거를 남긴다.
- 전송 바이트와 React 렌더링을 분리하고 진행률 표시 갱신을 제한한다. 작은 상태 변경 때문에 전체 앱을 계속 다시 그리지 않도록 한다.
- 최초 목록·더 보기·단축어 발급 등 대기 중인 동작은 중복 요청을 막고 해당 위치에 피드백을 제공한다.
- 기본 화면에 사진·영상·3D·외부 폰트 등 과업과 관계없는 초기 다운로드를 추가하지 않는다.

## 14. 기술·데이터·개인정보 조건

React·TypeScript·Vite와 현재 Worker API를 기준으로 구현한다. 디자인 시스템 또는 컴포넌트 패키지 도입은 번들·접근성·유지관리 근거를 평가한 후 결정한다.

| 계층 | 변경 범위 | 지켜야 할 계약 |
| --- | --- | --- |
| 화면·스타일 | 전면 교체 가능 | 기존 URL·직접 진입·파일 정보 보호 |
| API client/UI adapter | 상태·오류 해석·중복 요청 제어 개선 | 쿠키·CSRF·권한 전달 규칙 유지 |
| 업로더 통합 | 명시적 시작, 확인 지연 구분·결과 재조회 개선 | part 동시 수·idempotency·중복 수신 방지·전송 ID 유지 |
| Worker·D1·R2 | 현재 인증/전송 계약을 사용 | 이번 PRD만으로 보관·quota·인증 정책 변경 안 함 |

수정에 앞서 `App.tsx`의 화면 상태와 `UploadEngine`의 전송 상태를 분리한다. UI route의 mount/unmount 때문에 엔진을 새로 생성하지 않는다. FR-UP-03의 승인 전 대기 파일과 승인된 처리 대기를 구분하는 계약이 필요하다.

`QueueView`에는 현재 오류 문자열만 있고 API 오류 코드·정확한 취소 가능 여부·확인 지연 전용 상태는 없다. 이를 디자인만으로 가정하지 않는다. 구현 단계에서 필요한 최소 상태를 전달해 `FINALIZE_PENDING`·폐기·권한 만료·취소 경합을 정확히 분기한다.

PIN·TOTP·토큰·파일별 권한·signed URL을 로그·analytics·session replay·URL·localStorage에 저장하지 않는다. 인증 전 파일 목록을 미리 요청하거나 숨겨진 DOM에 넣지 않는다. 다운로드 세션 만료 시 목록 메모리와 표시를 정리한다.

잠금/폐기는 이미 발급한 R2 다운로드 URL이나 이미 열린 HTTP 전송을 즉시 회수하는 기능이 아니다. 저장된 다운로드 파일·OS 최근 파일·브라우저 다운로드 이력도 지우지 않는다. 안내와 검증은 이 범위를 따른다.

## 16. 검증 시나리오와 출시 기준

아래 시나리오를 요구사항 ID와 함께 검증 기록에 연결한다.

| ID | 시나리오 | 통과 기준 |
| --- | --- | --- |
| QA-01 | 최초 `/` 진입→PIN 인증→파일 받기 | 인증 전 정보 0건, 대상 다운로드 접근 가능, 기억 OFF |
| QA-02 | TOTP 공용 인증→2개 선택→보관 변경→시작 | 신뢰 OFF, 승인된 파일만 시작, 완료 후 보관 시각 정확 |
| QA-03 | 전송 중 새 파일 선택 | 기존 전송 유지, 새 파일은 명시적 시작 전 서버 생성 안 됨 |
| QA-04 | 업로드 중 받기/기기 화면 이동→복귀 | 전송 ID·파일 권한·현재 진행 유지, 중복 생성 없음 |
| QA-05 | 공용 인증 만료→재인증 | 활성 전송 계속, 미시작 파일은 대기, 재인증 후 승인된 항목만 시작 |
| QA-06 | 연결 끊김→재연결 | 확인 상태 표시, 서버 수신 part 중복 전송 없음 |
| QA-07 | 100%→파일 확인 지연→READY | 확인 전에 성공 표시 없음, 기존 결과 조회 후 완료 표시 |
| QA-08 | 취소 요청 실패/완료 경합/접근 종료 | 서버 미확정 상태를 성공으로 숨기지 않음, 종료 범위 문구 일치 |
| QA-09 | 다운로드 인증 만료·잠금·마지막 파일 만료 | 목록 정리, 새 요청 거부, 파일 보관 만료와 세션 만료 구분 |
| QA-10 | 더 보기 성공·실패·새로고침 실패 | 중복 행 없음, 조회 범위 정확, 기존 항목 유지/401 정리 |
| QA-11 | 대상 기기 해제·현재 기기 해제 | 대상별 재인증, 후속 권한 차단과 화면 갱신, 다른 등록 유지 |
| QA-12 | 단축어 토큰 생성·복사 실패·닫기 | 1회 표시 안내, 수동 복사 가능, 닫은 뒤 재표시/로그 없음 |
| QA-13 | 0바이트·상한 초과·50개 초과·긴 한글 파일명 | 올바른 사전 오류, 기존 목록 보존, 모바일 정보 누락 없음 |
| QA-14 | 키보드·스크린리더·확대·네 화면 폭 | 핵심 과업 완수, 포커스 복귀·오류 읽기·가로 overflow 기준 통과 |
| QA-15 | 받기 목록의 삭제→취소/Escape | 대상 전체 이름·복구 불가 안내, 취소 시 삭제 요청 없음, 포커스 복귀 |
| QA-16 | PIN 인증 + 신뢰 브라우저에서 파일 1개 삭제 | 추가 TOTP 없이 확인 후 선택 파일만 DELETED, 다른 파일 유지, 새 다운로드 차단 |
| QA-17 | 신뢰되지 않은 브라우저의 삭제 | PIN만으로 거부, 대상에 묶인 새 delete_file 코드로 허용, 일반 관리/공용 업로드 권한·다른 대상 grant·재사용 grant 거부 |
| QA-18 | 삭제 중 중복 클릭·세션 만료·다른 요청과 경합 | 중복 실행 방지, 권한 재확인, DELETE_IN_PROGRESS를 성공으로 표시하지 않음 |
| QA-19 | 저장소 삭제 실패→자동 정리→재조회 | DELETE_FAILED 안내, 미확정 물리 삭제를 완료로 표시하지 않음, 정리 후 DELETED·용량 1회 반환 |
| QA-20 | 삭제 후 모바일 목록·키보드 포커스·업로드 이력 | 삭제/다운로드 구분, 행 제거 후 합리적 포커스, ‘이 화면에서 지우기’가 서버 파일을 삭제하지 않음 |

프런트엔드 리디자인 출시에는 다음 조건이 필요하다.

1. P0 요구사항과 QA 시나리오에 미해결 차단 항목이 없다.
2. 선택한 디자인 방향의 화면·상태·문구·컴포넌트 계약이 구현과 일치한다.
3. `npm run check`와 `npm run deploy:check`를 통과하고 변경된 전송 동작을 검증한다.
4. 합성 파일로 작은 파일·여러 파일·64 MiB 경계 초과 전송을 검증하고 다운로드한 파일의 크기·해시를 대조한다.
5. 인증 전 정보 노출·의도하지 않은 신뢰 등록·중복 업로드·폐기 권한 사용·잘못된 대상 삭제·삭제 권한 우회·실패를 성공으로 표시하는 결함이 없다.
6. 브라우저/실기기 검증 증거와 남은 제한을 기록한다. iOS 검증이 없으면 지원 안내를 제한하고 미검증으로 남긴다.

이 기준은 리디자인의 회귀 검증이다. 기존에 남아 있던 1/5/16/32 GiB 실측·복원·대규모 정리 검증을 완료한 것으로 대체하지 않는다. 배포 시에는 기존 UI로 되돌릴 수 있는 프런트엔드 버전을 보존한다.

## 17. 후속 작업과 산출물

| 단계 | 작업 | 완료 산출물 |
| --- | --- | --- |
| 1. 기준선 정리 | 현재 세 과업의 단계·오류·소요시간과 기술 제약 기록 | 현재 흐름표, 상태/API 대응표, 측정 조건 |
| 2. 구조 비교 | A/B/C 디자인 방향의 같은 과업 비교 | 모바일/데스크톱 wireframe, 선택 근거 |
| 3. 시각·상태 설계 | 선택안의 시각 체계와 전체 P0 상태 설계 | 디자인 토큰, 컴포넌트 상태표, 화면 시안, 한국어 카피 |
| 4. 프로토타입 평가 | 받기·올리기·종료와 예외 흐름 시험 | 과업 관찰 기록, 수정 목록, 요구사항 대응 |
| 5. 구현 | 앱 셸·인증→업로드 통합→받기→기기 관리 순으로 연결 | 실제 API를 쓰는 UI, 필요한 엔진 상태 계약 변경 |
| 6. 회귀·출시 | 접근성·전송·권한·실기기·빌드 검사 | QA 기록, 알려진 제한, 배포 및 복귀 절차 |

시안에는 예시 데이터임을 표시하고 실제 PIN·TOTP 등록 키·기기 토큰을 사용하지 않는다. 디자인 산출물은 현재 기본 화면 한 장으로 끝내지 않고 인증 전/후·전송 중·오프라인·확인 지연·만료·종료·파일 삭제 확인/재인증/처리/정리 지연·기기 해제·토큰 표시까지 포함한다.

### 후속 설계에서 결정할 사항

| 결정 | 현재 제안 | 결정 시점 |
| --- | --- | --- |
| 최종 레이아웃 | A. 전송 데스크를 우선 검토하되 B/C와 같은 조건에서 비교 | 구조 비교 후 |
| 기본 시각 테마 | 사용자 제공 Assemble 시스템, 대비·한글·작업 여백 보완 | 기준 채택 완료, 구현 시 실제 조합 검증 |
| 브랜드 링크 | 파일 받기 `/`로 통일 | 내비게이션 프로토타입 검토 시 |
| iOS 출시 안내 | 웹 흐름과 단축어 설정의 검증 범위를 각각 표시 | 실기기 시험 후 |
| P1 검색·정렬 | 첫 출시 제외, 전체 목록 계약 확보 후 검토 | P0 평가 후 |

현재 단계에서 추가 사용자 입력을 필수로 요구하지 않는다. 위 기본 제안으로 디자인 탐색을 시작할 수 있고, 최종 시각안과 실제 구현 범위는 후속 검토에서 확정한다.
